Your agent is one prompt away
from disaster

A system prompt that says "never reveal PII" is a suggestion, not a guarantee. The traits that make agents useful make them hard to constrain.

→ tool.pre_invoke · ESCALATE

→ input.received · DENY / OBSERVE
How it works

One event in.
One composed verdict out.

An event fires in your agent. APL builds a PolicyEvent, fans it out to every connected policy server, composes the verdicts into one decision, and enforces it. If a server can't be reached, it fails closed.

Features

A protocol for agent constraints

Where MCP gives a model capabilities through a uniform protocol, APL applies constraints through one.

🔌

Runtime-agnostic

One policy, any agent stack — raw OpenAI or Anthropic calls, a LangGraph graph, or something bespoke.

🎯

Rich verdicts

Not just allow / deny. Modify a payload, escalate to a human, or observe for audit — five verdicts, one vocabulary.

🔒

Fail-closed by default

A guard you can't consult is a guard that says no. Timeouts, errors, and unreachable servers deny — never silently skip.

📝

Declarative or code

Author policies in Python, or in YAML with no Python at all. Serve a .yaml exactly like a .py.

⚡

One-line auto-instrument

Patch OpenAI, Anthropic, LiteLLM, LangChain & watsonx in place. Every call flows through your policies.

🔗

Composable

Run many policy servers at once. Verdicts merge with defined semantics — deny-overrides, unanimous, weighted & more.

Quickstart

Author a verdict.
Then enforce it live.

Write a policy, see it in isolation with one CLI call, then put it in front of your LLM with a single line. That's the whole loop.

Read the docs Browse examples 
import re
from apl import PolicyServer, Verdict

server = PolicyServer("guard")

@server.policy(name="redact-ssn", events=["output.pre_send"])
async def redact_ssn(event):
    text = event.payload.output_text or ""
    if re.search(r"\d{3}-\d{2}-\d{4}", text):
        return Verdict.modify(
            target="output", operation="replace",
            value=re.sub(r"\d{3}-\d{2}-\d{4}", "[SSN REDACTED]", text),
            reasoning="Redacted SSN",
        )
    return Verdict.allow()

if __name__ == "__main__":
    server.run()  # stdio by default
# Try it — no agent required
$ apl test ./guard.py -e output.pre_send \
    -p '{"output_text": "Your SSN is 123-45-6789"}'

Safe by default

A guard you can't consult
is a guard that says no.

  • ✕Unavailable → deny. A policy that times out, errors, returns a non-verdict, or whose server is unreachable resolves to deny. Enforcement is never silently skipped.
  • !Fail-open is explicit and loud. FailMode.OPEN must be passed deliberately — and warns at startup.
  • ⏲The layer timeout fails closed too. A bounded evaluation returns deny on expiry.

Composition

Many policies. One decision.

When several policies weigh in on one event, a composition strategy reduces their verdicts to a single enforceable decision.

ModeHow verdicts combine
deny_overridesAny deny wins; else escalate; else apply all modify; else allow.default
allow_overridesAny allow wins; else modify; else escalate; else deny.
unanimousEvery non-observe verdict must be allow, otherwise deny.
first_applicableFirst non-observe verdict wins, in priority order.
weightedConfidence × per-policy weight vote; escalate short-circuits; deny breaks ties.

FAQ
What are AI agent guardrails?
Guardrails are enforceable constraints around an AI agent's behavior. APL provides lifecycle hooks and a verdict vocabulary — allow, deny, modify, escalate, observe — to enforce them at runtime, independent of the framework the agent is built on.
How is APL different from existing guardrail solutions?
Most guardrails are tied to one runtime. Provider-native filters — AWS Bedrock Guardrails, say — only protect models invoked through that provider, with a fixed taxonomy of block / mask rules. APL is runtime-agnostic: the same policy guards OpenAI, Anthropic, LiteLLM, LangGraph, watsonx or a bespoke agent. You bring your own detection (a regex, a classifier, an LLM call) and get five verdicts instead of just block — allow, deny, modify, escalate, observe — compose many policy servers into one decision, and fail closed by default. Change model providers and your guardrails come with you.
Can my security and AI engineering teams work independently?
Yes — that separation is the whole point. Your security / platform team owns the policy servers: they author and host the constraints (locally over stdio, or shared org-wide over HTTP) and update them without ever touching the agent. Your AI engineering team builds the agent and connects to the policy layer with one line of auto-instrumentation — they don't write, own, or redeploy policies. And because policies are hot-swappable, security can tighten a rule in production with no agent redeploy. It mirrors MCP's split: capabilities on one side, constraints on the other, each owned by the team responsible for it.
How is APL different from a system prompt?
A system prompt that says "never reveal PII" is a suggestion, not a guarantee. APL enforces constraints in code at the agent's lifecycle boundaries — input, LLM request, tool call, output — and fails closed if a policy can't be consulted.
What does "fail-closed" mean?
If a policy times out, errors, returns a non-verdict, or its server is unreachable, APL denies the action by default rather than letting it through. Fail-open (FailMode.OPEN) is an explicit, logged opt-in.
Which frameworks and LLM providers does APL support?
APL is runtime-agnostic: it works with OpenAI, Anthropic, LiteLLM, LangChain, LangGraph, watsonx, and any custom agent stack. One-line auto-instrumentation patches the installed SDKs in place.
Is APL open source and free?
Yes. APL is open source under the Apache 2.0 license and available on PyPI as agent-policy-layer. It's pure Python with no external services required.
How is APL like MCP?
Where MCP gives a model capabilities through a uniform protocol, APL applies constraints through one — the same lifecycle hooks and verdict vocabulary regardless of how the agent is built.
